## 1. 设计目标（完成定义，对齐路线图 §15 6/5 标准）

| # | 标准 | 本计划如何满足 |
|---|---|---|

## 2. 数据契约（公开 API）

### 2.1 玩家职位新接口（全部挂 `window`）

```js
// 旧（v18.8）：discipleState 仅 RAM，rankId=0..7
// 新（v19.0）：保持 rankId 0..7 编号；新增 derived 字段
getPlayerRank()        // → {id, name, desc, privileges, duties, salary, dailyTaskCount, promoteCondition}
getPlayerDailyTaskLimit() // → number
getPlayerRankAuthority() // → 0-10（长老/掌门才有 >5）
canAccessScriptureTier(tier) // → bool（藏经阁）
canVoteInSectMeeting() // → bool
canDecideSectPolicy()  // → bool（掌门级）
getPlayerSectRole()    // → 'disciple' | 'elder' | 'leader'
```

## 5. 批次实施

### 批次 A：discipleState 真源化（**核心基础设施**）

**目标**：让 player rank / contribution / points 在读档后保留。**不改变任何玩法**。

| 步骤 | 内容 | 自检 |
|---|---|---|
| A1 | 在 `sects-system.js` 末尾注册 `StateRegistry('discipleState', v1)` | export/import/reset |
| A2 | 提供 `getPlayerRank() / getPlayerDailyTaskLimit() / getPlayerRankAuthority() / getPlayerSectRole()` | 单元断言 |
| A3 | `acceptTask` 改为先调 `getPlayerDailyTaskLimit()`，超限返回 false | 玩家不能超 dailyTaskCount |
| A4 | 修一条已知 bug：`sectPromote` 直接 `ds.contribution -= reqAmt`，但没 clamp 到 0 | 极端情况贡献 < reqAmt 时不退化为负数 |

**完成定义**：node 断言 + 浏览器实测 `discipleState.contribution` 改变后 export → reload → importAll 数值一致。

### 批次 B：玩家特权生效（**4 类玩法**）

**目标**：职位真的改变玩法。

| 步骤 | 内容 |
|---|---|
| B1 | 藏经阁：tier 准入改用 `canAccessScriptureTier(tier)`（映射 COMMON_RANKS.id → tier） |
| B2 | 演武场：玩家 rank ≥ 长老才能开启"演武场教弟子"任务（rankId ≤ 2） |
| B3 | 议事投票：长老及以上（rankId ≤ 2）有 `voteInSectMeeting(voteId, choice)` |
| B4 | 掌门决策：rankId === 0 可 `decideSectPolicy(policyId, args)`；需长老过半数确认 |
| B5 | 任务分发 UI 加 rank 限制提示（无实现改 UI，文案"长老方可接取"） |

**完成定义**：4 类玩法各 1 条断言；长老以下 `canAccessScriptureTier(4) === false`；长老可 `canAccessScriptureTier(3) === true`。

### 批次 C：年度宗门目标（**P0-3 验收核心**）

**目标**：玩家入宗时 5 选 1 选择年目标；日结推进进度；年末结算。

| 步骤 | 内容 |
|---|---|
| C1 | 新建 `js/sects/sect-year-goal.js`：5 选 1 + 日结 tick + 年末结算 |
| C2 | StateRegistry `sectYearGoal` v1（per-sect 当前目标 + 历史） |
| C3 | `processAllSectDailyEconomy` 末尾追加 `SectYearGoal.tickDay(day)` |
| C4 | UI：入宗时弹"年度目标选择"模态；宗门面板加"年度目标进度"卡片 |
| C5 | 年末结算（新年后 day=1 触发）：判定是否完成，发奖，写 log |

**完成定义**：5 选 1 模态可正常关闭；日结推进进度正确；年末结算逻辑断言。

### 批次 D：宗门议事投票（**P0-3 权力机制**）

**目标**：长老可投票、掌门可决策，落到宗门资源/士气。

| 步骤 | 内容 |

| D1 | 新建 `js/sects/sect-vote.js`：投票生命周期（open / cast / close）+ 24h 窗口 |

## 9. 风险与不做清单

### 风险
- **R1 dailyTaskCount 限制可能误伤**：若玩家已经接了 N 个任务，需要先交才能再接。UI 必须明确提示
- **R2 年末结算可能与 NPC 状态冲突**：跨年夜 NPC 寿命/境界会变化，年末结算应放到 day=1 触发而不是 day=360
- **R3 投票 24h 窗口**：玩家若闭关 30 日，投票可能错过窗口。**缓解**：闭关期间投票自动弃权（不计入通过票也不计入反对票）
- **R4 掌门决策 + 长老过半数**：单玩家 + 1 NPC 掌门情况下，"长老过半数"可能卡死。**缓解**：若 NPC 长老不足，过半数按"在场长老"算

### 明确不做（v19.0）
- NPC 投票立场（v19.1）
- 同门竞争/弹劾（v19.1）
- 弟子/长老专属门派建筑（如亲传弟子的独立院落，UI 不动）
- 多重年目标（一次只 1 个）
- 玩家被贬职（v18.8 路线图未提）
